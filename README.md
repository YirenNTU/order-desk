# 下單程式

每位用戶用自己的電腦和永豐帳戶。GitHub 上共用的是程式和每週權重。金額、API、憑證、帳本、log 留在自己的電腦。

目前發布的策略是 `super_alpha_4`、`super_alpha_5`、`rolling_top_10`。

`git pull` 會更新程式和 `strategies/<名稱>/signal.json`。它不會改 `.env`、`config.json`、`strategies/<名稱>/ledger.json`、`logs/`。

## 安裝

```bash
git clone https://github.com/YirenNTU/order-desk.git
cd order-desk
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp config.example.json config.json
cp .env.example .env
```

## 設定

`.env` 照 `.env.example` 填自己的 API、帳號、憑證。正式下單加上：

```bash
TRADING_ALLOW_PRODUCTION=YES_I_ACCEPT_REAL_ORDERS
```

執行 `python -m order_desk` 時會自動讀這個 `.env`，不用另外 export。

`config.json` 照 `config.example.json`。

- `name` 必須等於 `signal.json` 的 `strategy_id`
- `extra_twd`：這次要加進這個策略的現金。第一次買填這裡。它會留到你改回 `0`；沒改回的話，下次計畫會再加一次
- `cash_out_twd`：要提出的金額。大於 0 會賣掉這個策略多出來的股票
- `adjust_positions`：每個策略分別設定，缺欄位或 `true` 會參與新計畫。`false` 在建立新計畫時保留該策略持股，不跟新權重調倉、不加錢、也不提領。策略仍要留在 `config.json`；開關持續生效，直到改回 `true`。不會取消已掛單或中止已保存的舊計畫，詳見下方。
- `mode`：`simulation` 模擬，`production` 正式
- `lot_mode`：`odd` 零股，`common` 整張
- `cash_check`：正式模式強制啟用資金安全檢查；即使舊設定為 `false` 也不能略過。模擬模式可明確關閉。詳見下方「資金安全檢查」。
- `schedule.enabled`：`false` 時已安裝的排程在下一次檢查起不再啟動拉權重或下單工作；不會中斷正在執行的程序或撤銷已掛單。缺欄位視為開啟
- `schedule.git_pull` / `schedule.order`：台北時間。從每週第一個開盤日到週五，到了時間就拉權重或補下單；週一休市就順延
- `restricted_order_policy`：預設 `freeze_reweight`，券商已確認預收／圈存限制導致失敗時，記錄待處理股數，保留受限持股、扣除其占用資金後重新配置。`stop` 保持停止處理。不是忽略所有注意股或所有下單失敗。
- `inventory_mismatch_policy`：預設 `reconcile_actual`，依核對後的實際策略持股調整帳本並重算配置；`quarantine` 隔離有差異的股票；`stop` 遇到差異即停止。這些模式都不會把結果不明的委託當成未成交。
- `cash_fee_rate` / `cash_min_fee_twd`：買單預留手續費的比例與每筆最低金額，預設分別為 `0.001425`、`20`。保留較高者；不是券商實際收費保證。

帳本裡已經有股數的策略都要留在 `config.json`。拿掉之後，整份計畫會拒絕執行。

股數 =（這個策略帳上股票的現值 + `extra_twd` − `cash_out_twd`）× 權重 ÷ 現價。帳本不存總金額，現值是下單當下用股價現算的。

每週權重在 `strategies/<名稱>/signal.json`，有效時間要蓋住當週交易日。`adjust_positions` 為 `false` 的策略即使 signal 過期，也不會擋住其他策略。

### 只調整部分策略

例如想保留 `super_alpha_4`、`super_alpha_5` 的持股，只讓 `rolling_top_10` 參與新調倉，可以使用以下完整設定。範例採 `simulation`；正式使用時才改為 `production`，並填好自己的 `.env` 與正式下單授權。

```json
{
  "strategies": [
    {
      "name": "super_alpha_4",
      "signal_path": "strategies/super_alpha_4/signal.json",
      "extra_twd": 0,
      "cash_out_twd": 0,
      "adjust_positions": false
    },
    {
      "name": "super_alpha_5",
      "signal_path": "strategies/super_alpha_5/signal.json",
      "extra_twd": 0,
      "cash_out_twd": 0,
      "adjust_positions": false
    },
    {
      "name": "rolling_top_10",
      "signal_path": "strategies/rolling_top_10/signal.json",
      "extra_twd": 0,
      "cash_out_twd": 0,
      "adjust_positions": true
    }
  ],
  "mode": "simulation",
  "lot_mode": "odd",
  "cash_check": true,
  "schedule": {
    "git_pull": {"weekday": "monday", "time": "08:00"},
    "order": {"weekday": "monday", "time": "09:20"},
    "enabled": true
  },
  "restricted_order_policy": "freeze_reweight",
  "inventory_mismatch_policy": "reconcile_actual",
  "cash_fee_rate": 0.001425,
  "cash_min_fee_twd": 20
}
```

請使用 JSON 布林值 `false` / `true`，不要寫成字串 `"false"` / `"true"`。暫停不是清倉，也不會把這個策略的資金移給其他策略。若策略尚無持股且 `extra_twd` 為 0，即使開啟也不會憑空產生投入資金。恢復前檢查 `extra_twd`、`cash_out_twd`：暫停期間雖然不套用這兩個值，恢復後的新計畫仍會讀取它們。

### 設定何時生效

| 情況 | 實際行為 |
| --- | --- |
| 尚未建立計畫 | 新計畫依各策略的 `adjust_positions` 決定是否調倉。 |
| 已有券商掛單 | 改成 `false` 不會撤單；既有委託仍可能成交，程式仍需核對並記帳。 |
| 當天已有未完成計畫 | 續跑可能沿用已保存的訂單，不會只因改成 `false` 就停止該策略。 |
| 跨日或受限股需要重算 | 先釐清舊委託，再檢查已保存預算與訊號。同一調倉週期中改動 `adjust_positions` 會改變訊號摘要，重算時可能因與原計畫不符而停止。 |
| 要暫停整個自動排程 | 設 `schedule.enabled` 為 `false`，後續排程檢查會停止啟動工作；不會中斷已開始的程序或撤銷券商掛單，也不阻止手動執行下單指令。 |

因此，`adjust_positions: false` 適合在新一輪計畫開始前設定，不是當天未完成單的立即停止開關。不要刪除策略、帳本或未完成紀錄來強迫重算。帳務核對仍會運作；若實際庫存有差異，`reconcile_actual` 仍可能調整記帳股數並留下原因。

### 更新後保留每位使用者的設定

`git pull` 更新程式、文件、範本及策略權重，不會把 `config.example.json` 自動覆蓋到既有的 `config.json`。已有使用者只需在自己的設定中加入需要的欄位；不要重新複製範本覆蓋個人設定。`adjust_positions` 沒填預設為 `true`，其餘新增政策的預設值如上。

歷史帳務跨日核對不需要另加開關，更新程式後會由既有核對流程使用。每位使用者使用自己的券商帳戶、帳本和歷史證據，不能沿用其他人的成交或已扣款確認。已安裝的排程每次啟動新程序讀取目前版本；正在執行的舊程序不會中途換版。

## 下單

```bash
python -m order_desk
python -m order_desk --send --confirm APPROVE
```

第一行是預覽，不送新單，但會先向券商核對委託並寫回帳本。查不到的委託會保留為待核對，不能當作未成交。第二行才送出 `config.json` 裡每個策略的單。

買單掛漲停，賣單掛跌停，先賣再買。漲停是出價上限，不保證成交。中斷後同日續接原始計畫；跨日先核對舊委託；確認結束後以當天價格重新規劃剩餘差額，保留原調倉預算，不會漏掉已賣出待配置資金或重複加錢。未確認的委託不能直接當成未成交。

## 帳本

成交後的股數記在 `strategies/<名稱>/ledger.json` 的 `positions`，會一直累加。還沒結束的委託暫存在同一個檔案的 `open_orders`。這個檔案不要上傳，`git pull` 也不會改它。首次儲存後，`logs/ledger.sqlite3` 是整本帳的權威來源；各策略 JSON 是可恢復的檢視副本，不要手改。SQLite 保留每次變動快照、完成委託歷史及未完成計畫；備份時須一併備份整個 `logs/`。

## 每週自動

```bash
python -m order_desk --install-schedule
python -m order_desk --uninstall-schedule
```

安裝後，LaunchAgent 每分鐘檢查一次。電腦要開著並已登入。

- 每週第一個開盤日到週五：到達 `schedule.git_pull`（預設 08:00）且當天還沒拉成功，就做 `git pull --ff-only`
- 同一區間、到達 `schedule.order`（預設 09:20）、盤中 09:00–13:25、且本週還沒完成下單：當日 pull 成功才送單
- 週一休市會順延到該週下一個交易日
- 第一天沒開機、過了盤中、或送單失敗：後面的交易日會再拉一次並補下單
- 送單意圖會先寫入帳本再送券商。回覆遺失時以唯一識別碼核對，無法確認則停止；完成委託永久保留。中斷後同日延續原計畫；跨日確認舊單結束後重算剩餘差額，不重送已成交股數
- 本週全部成交，或本來就沒有需要的單：後面幾天不再下單
- 週五盤後仍沒完成：留到下週第一個開盤日，用新的一週權重重算
- 13:40 後有未完成計畫時，每五分鐘核對一次委託，直到取得最終結果；此流程只記帳，不下新單
- `logs/last_order.json` 記本週狀態：`completed`、`completed_with_deferrals`、`working`、`failed`。前兩者算本週完成；預收／圈存受限股票留到下一個調倉週期

要暫停排程：把 `config.json` 的 `schedule.enabled` 設成 `false`，下一分鐘生效。要改時間或星期：改 `schedule.git_pull` / `schedule.order` 即可，不用重裝。只有換電腦、換 Python，或 config 路徑變了，才要再跑 `--install-schedule`。要卸掉 LaunchAgent 用 `--uninstall-schedule`。

當天 pull 失敗，或查不到休市日，就不會下單。也可以隨時手動執行上面的下單指令。

`git pull` 更新的是 repo 裡已追蹤的檔案，包含程式碼和 `strategies/<名稱>/signal.json` 的新權重。它不會改 `.env`、`config.json`、帳本、`logs/`，也不會動券商那邊的委託。

## 下單前雙重核對與異常處理

```bash
python -m order_desk --audit
```

只查券商持股與當日委託，不送單、不修改持股。最新報告寫在 `logs/account_audit.json`，每次核對亦保存在 `logs/account_audit.sqlite3`，保留當時觀察到的程式與來源未確認委託，逐股列出券商股數、策略帳本股數及未分配差額，並將委託分成 `program`（程式紀錄可對應）、`external`（手動／帳外）和 `unattributed_program_tag`（帶程式標記但本機缺少紀錄）。正常手動成交不需要逐筆確認，也不自動歸入策略。

每次新計畫送出前、以及賣單完成轉買單前都會再核對。策略股數超過券商或扣除帳外股數後不一致時，依 `inventory_mismatch_policy` 對帳調整或隔離，詳見下方「避免整批卡住」。未知程式標記及無法確認是否已送出的委託仍會停止新單。正常手動買單和帳外股數足夠的手動賣單不會單獨造成阻擋。實際送單與對帳全程加鎖，避免手動啟動和排程同時執行。

已確認取消／失敗的單不會自動重送。檢查 `broker_snapshot.status_detail` 的失敗原因，確定要同日重試原計畫剩餘股數後才執行：

```bash
python -m order_desk --send --confirm APPROVE --retry-terminal
```

這會真的送單。`Unconfirmed`／`SubmissionUnknown` 不可用這個選項跳過。跨日原計畫必須另行核對和重新審閱價格；不能直接沿用昨日限價。舊帳修復須有券商成交與策略分配證據，不能只把帳本壓到目前庫存。

沒有策略帳本的舊式設定不再允許送單。`--audit` 無法證明券商不提供的歷史成交完整，也不能排除核對之後另一個裝置立即下單；請避免在同一股票上同時操作。

## 受限股票：扣除持股價值後重新配重

`config.json` 可設定 `"restricted_order_policy": "freeze_reweight"`（未設定時也採用此預設；可明確設 `"stop"` 改回嚴格停止）。只有券商已確認 `Failed`、且回覆要求預收／圈存的委託會走這個流程；未確認、仍在成交中、餘額不足及帳差都不能忽略。

1. 先核對並入帳已成交部分，將失敗委託及未成交股數記入 `deferred_orders`。
2. 本調倉週期暫停該股票的買賣，各策略保留實際持股。假設持有 7 股、原想賣 3 股，會先保留全部 7 股，避免另外 4 股被重複配置。
3. 該策略可交易資金＝原調倉預算－受限持股數×最新估值價格。其他標的依原權重的相對比例重新分配，股數向下取整；沒用完的額度不強迫下單。原本沒有受限股票的策略保留其已核定目標。
4. 未完成的調倉使用儲存的原始預算，不能只拿賣出後剩餘股票估值，也不會再次套用加錢／提領設定。舊計畫缺少預算資料時須先有證據補齊，不能猜。若配重尚未送出便跨入下一週，使用新週期權重與即時價格，解除舊凍結，但保留未完成計畫的資金上限，不重複加錢。
5. 預覽會顯示凍結價值、可配置預算與新股數。`--send --confirm APPROVE` 才依新計畫下單；不會繼續執行配重前的舊買單。遇到新受限股，紀錄後在下一次執行重新配重，避免無限重送。

週期以台北時間週一開始的一週為單位，休市則由既有排程順延。當可交易部分完成，狀態為 `completed_with_deferrals`，同一週不反覆下單。下一週解除舊週期的凍結，依最新目標重新規劃：需要賣出便再試，最新目標無需交易則記錄該判斷。再次遭拒會留下新紀錄並重新配重。

帳本 `deferred_orders` 保留原委託、策略分配、未成交股數、原因、所屬週期、下次可重試日期及 `retry_checks`；後續實際送單和成交可透過其 `client_order_id` 對應 `order_history`。歷史不會因為進入下一週而刪掉。`--audit` 也會列出這些紀錄。

重新配重控制的是策略估值預算，並不取代交割資金確認；正式模式的資金安全檢查與成交核對仍照常執行。若受限持股現值已超過策略預算，程式會停止要求處理，不會產生負的可用資金。

## 手動部位與策略部位分開核對

核對式為：**券商總持股 − 手動／帳外持股 = 策略帳本持股**。

- 以第一次可用的對帳紀錄建立帳外持股基準；之後只依觀察到的手動累計成交增量調整帳外股數。手動買進增加帳外部位，手動賣出扣掉帳外部位，策略帳本不因此改動。
- 部分成交、部分成交後取消、重複回報、重啟和券商跨日不再回傳舊單，都使用已保存的委託觀察值核對，不會重複扣除。
- 例如券商有 30 股，策略 20 股、帳外 10 股；手動賣出 8 股後，券商 22 股、帳外 2 股、策略仍為 20 股，可以繼續。若手動賣出 12 股，便可能動到策略持股；在 `reconcile_actual` 模式會依券商庫存調整實際策略股數，並留下獨立對帳調整，而不是偽造一筆成交。
- 正常手動成交無須確認歸屬或核准。未知程式識別碼及累計成交倒退仍會阻擋。一般庫存差異依下方規則調整；不能靠忽略未知委託來續送。

報告新增 `external_shares`、`strategy_shares_after_external` 與 `difference_shares`。`logs/account_audit.sqlite3` 保存基準及各委託最新觀察，備份帳本時要一起保留。初始基準不是啟用前的完整交易重建；未被券商查詢或既有紀錄涵蓋的歷史變動，仍需另外核對。核對後其他裝置又立即交易的競態，也無法只靠一次查詢完全消除。

## 避免整批卡住：按核對後的實際部位重新配置

目前預設 `"inventory_mismatch_policy": "reconcile_actual"`；舊 config 缺少這個欄位也會套用。支援三種模式：`stop` 保持嚴格停止；`quarantine` 隔離有差異股票、扣除其占用資金後交易其餘標的；`reconcile_actual` 依實際可用股數對帳調整，再重算配重。

`reconcile_actual` 流程：

1. 先核對程式委託、累計成交及手動／帳外部位。未知程式委託、重複或倒退的成交回報不能以改帳跳過。
2. 實際可歸策略股數以「券商股數減掉非負的帳外持股」為上限，也不超過原策略帳本宣告的股數。無法解釋的多出持股留在帳外，不拿來增加策略資金。
3. 若策略股數確實不足，同股票的缺口按各策略原股數比例分攤，以最大餘數法分配整數股；不會讓任何策略出現負股數。
4. 尚未開始的計畫依修正後持股現值重算。正在執行的計畫，保留已保存的原調倉資金上限，再扣除少掉股數按當前價格估值的金額，避免已賣出、尚未買回的待配置預算遺失。這是策略配置上限，不是銀行可用餘額；不會自動把未歸屬策略的手動賣出款加進來。買單另須通過正式模式強制的資金安全檢查。
5. 受影響策略重新計算目標股數，不沿用超過修正後預算的舊目標。已成交的單不重送，只執行剩餘差額。
6. `inventory_adjustment_history` 保存券商股數、各策略調整前後股數、帳外股數、估值價格、預算調整與原因；種類明確標示為 `reconciliation_adjustment_not_broker_fill`。原始券商成交歷史保持不變。

手動賣單仍在等待成交、可用股票被占用時，該股先進入 `inventory_quarantine`，其他標的可以繼續。後續核對恢復一致會解除，並在 `inventory_quarantine_history` 留下紀錄。

送單前或賣轉買時如持股變動，單次執行最多自動重新核對與規劃三次；持續變動則保存進度，交由下一次排程再試，不會無限迴圈。券商斷線或無法確認送單結果時仍保留委託等待核對，不能為了續跑而重送。

預覽也可能產生上述有憑據的對帳調整紀錄，但不送委託；`--audit` 仍是純查詢。恢復排程或使用 `--send --confirm APPROVE` 才會實際交易。


## 更新後繼續執行

一般用戶在自己的 Order Desk 目錄執行 `git pull --ff-only` 即可取得最新程式。排程每次啟動都從該目錄載入程式；當次拉取成功後，另開新的 Python 程序執行，避免沿用更新前已載入的程式。本次沒有新增套件依賴，也不需要重新建立環境。

舊 config 沒有異常處理欄位時，自動使用 `restricted_order_policy=freeze_reweight` 與 `inventory_mismatch_policy=reconcile_actual`。原本明確指定的設定、策略金額及排程暫停狀態不會被更新覆蓋。

若排程曾暫停，由帳戶使用者執行：

```bash
./.venv/bin/python -m order_desk --resume-schedule --confirm APPROVE
```

這會安裝／更新本機排程、將 `schedule.enabled` 設為 `true`，並立刻檢查本週剩餘計畫。交易日且仍在設定的送單時間內會執行剩餘訂單；已收盤則等待下一個交易日。這個指令會啟用真實交易（當 `mode=production`），執行前可先用不帶參數的預覽確認。

一般失敗、取消或部分成交的剩餘股數，取得券商最終結果後在下一交易日重新定價；同週保留原目標，下週改用新權重，且不重複套用 `extra_twd`。預收／圈存受限股票依前述規則等下一調倉日。

盤後核對保存最終委託快照，隔天券商當日查詢沒有舊委託時，可使用已保存的終止回報接續。若電腦關機、斷線或券商尚未回報終止結果，舊單仍保留待核對，不會把查不到的單當作零成交。這是避免重複買賣所需的例外。

券商查詢的日期範圍與更新方式依 [Shioaji 委託狀態文件](https://sinotrade.github.io/tutor/order/UpdateStatus/)；`--reconcile-only` 可單獨更新成交記錄，不會送出新委託。


## 台股規則審查（2026-11-09）

本版依 [證交所交易制度](https://www.twse.com.tw/zh/products/system/trading.html)、[櫃買零股規則](https://www.tpex.org.tw/zh-tw/mainboard/trading/rules/odd-lot.html)、[Shioaji 委託查詢](https://sinotrade.github.io/tutor/order/UpdateStatus/) 與 [庫存欄位定義](https://sinotrade.github.io/tutor/accounting/position/) 增加以下檢查：

- 官方年度日曆包含開始交易日、最後交易日，不能把每一列都列為休市。日曆快取格式升為 2；舊快取會重新下載並分類。2026-01-02、02-11、02-23 是交易日；僅結算交割日仍不交易。
- 只使用選定券商分公司及帳號的現股委託與 Cash 多方庫存；其他帳戶、期貨、融資與融券不混入現股策略。回報缺少必要帳戶識別時停止核對。
- 行情以股票代號對應，不依回傳陣列順序；漏列、重複代號會拒絕規劃。
- 一般整股與盤後定價（Fixing）的回報數量按交易單位換算；盤中／盤後零股按股數。現支援 TSE／OTC、每單位 1,000 股的現股商品；不同交易單位或市場會明確拒絕，避免錯算股數。
- 一般委託每筆最多 499 張，超過會拆單並保留唯一識別；盤中零股每筆 1–999 股。股數、券商數量、金額與策略分配在新單及續單都重新驗證。
- 買賣使用限價 ROD 現股委託。每一筆進入券商前，再確認交易日、09:00–13:25 的本程式送單窗口，以及最新合約的漲跌停範圍。13:25 是程式保留的緩衝截止時間，交易所盤中零股申報實際到 13:30。
- 本機檢查已確定未送出的單另存 `local_rejection_history`，不偽裝成券商成交，也不留成無法查到的未知委託；若已呼叫券商而回覆不明，仍保留待核對。

這些檢查不代表保證成交或零缺陷。斷線、其他裝置同時下單、臨時停市／停牌或預收條件仍須以券商／交易所回覆為準。年度日曆不保證涵蓋臨時事件。既有污染或缺漏的歷史資料也不會因更新自動完整重建。

配置預算仍以持股估值及保存的週期資金上限計算，並非含手續費、交易稅與 T+2 交割的精確現金帳。正式模式現在強制使用下述資金檢查。它是保守的送單限制，不是精確交割現金帳，也不保證查詢後帳戶不會再被其他操作動用。


## 資金安全檢查

正式模式每筆新買單前，都重新查詢[交割帳戶餘額](https://sinotrade.github.io/tutor/accounting/account_balance/)、[T／T+1／T+2 未交割資料](https://sinotrade.github.io/tutor/accounting/settlement/)與當日買單。銀行不支援、查詢失敗、資料缺漏、餘額時間超過兩分鐘或非有效數字，都不送新買單。信用交易額度不能替代銀行餘額。

正式模式的下單額度按交割日計算，與銀行即時餘額分開顯示。台股普通交易按 [T+2 應收、應付相抵後的淨額交割](https://www.twse.com.tw/zh/products/system/trading.html)。因此，**今天已成交且經核對的賣款可以抵今天新買單的交割款**，未成交賣單不計收入；這不是宣稱賣款已進銀行或可立刻提領。

先檢查 T／T+1 的付款有沒有缺口，再計算 T+2 買單額度。T+1 已確認應收可以支應較晚的 T+2 買款，但 T+2 的應收不能填補 T+1 的付款缺口。T 日交割款可能已反映在銀行餘額，應收不再加一次；若仍有應付且 API 無法證明已扣帳，會明列 `today_settlement_status_unverified` 並保留，不憑時間猜測已扣帳。

同一日的已成交買賣與券商 T+2 交割款只計一次：取「券商有正負號的交割淨額」與「逐筆已成交賣款減買款的估計淨額」較小者，亦即保留較大的應付、採用較小的應收，再扣未成交買單的剩餘保留款。買款估計含手續費，賣款估計扣手續費及 0.3% 交易稅緩衝，ETF 或優惠費率可能更保守。若券商交割資料尚未更新，先採較低額度，下次檢查再更新。

畫面分列 `bank_balance`（銀行餘額）、`settlement_buying_power`（含核對應收的買單額度）及 `confirmed_receivables`；帳本另外記錄逐日 `settlement_timeline` 和較早付款缺口。隔日讀取滾動後的交割資料，前日成交紀錄不再重加。

手動單與程式單共用帳戶資金，均按委託識別碼合併。券商已確認撤單會釋放未成交餘額；部分成交只保留成交款及剩餘掛單，手續費不重複預留。本機剛送出、尚未出現在券商查詢的委託仍保留；券商回報成交量若少於本機已確認量，則重新核對而不放行。已成交市價單可依完整成交明細估值，仍未成交且沒有可驗證價格上限的市價買單會暫停新增買單。

新買單以限價乘股數預留本金，加上手續費緩衝，金額向上取整。預設 `cash_fee_rate=0.001425`、`cash_min_fee_twd=20`，每筆取比例費用與最低費用較高者；這是保留值，不是券商實際收費保證。兩個欄位可設定為較高的費用估計。逐筆估算與券商交割款採較保守的淨應付款核對。

資金不足時，賣出流程仍可繼續；新買單保持未送出，保存 `buys_waiting_for_cash` 進度。每次排程再檢查，交割額度足夠才接續剩餘買單，已送出的單不重送。此檢查不會自動撤銷既有委託。

`logs/ledger.sqlite3` 中的 `cash_safety` 與 `cash_safety_history` 記錄有正負號的交割明細、逐筆成交／未成交保留款、餘額、所需金額、缺口及停止原因；預覽及執行畫面也會顯示。這些私人紀錄不發布到 Git。

`git pull` 後正式模式即使用強制檢查，不必修改其他使用者的私有 `config.json`。仍需留意其他裝置可能在核對後操作同一帳戶；資金檢查無法替銀行鎖定餘額。

自動續跑會在帳戶鎖內檢查帳本的本週完成紀錄；即使外部排程完成標記遺失，也不會重新執行已完成週期。隔日須先確認前日每筆委託的最終成交，再依實際策略持股及原週期資金上限重算差額。普通持股差異可由 `reconcile_actual` 修正並留存調整紀錄；身分不明或缺少最終回報的舊委託仍需核對，不能猜成未成交後重送。

已扣帳交割款的處理：帳戶本人明確確認銀行已扣款時，可在本機帳本保存 `settlement_posting_confirmations`。確認綁定帳戶、交割日期、完整金額及確認時間；只有今日 T0 金額完全相符、且銀行餘額查詢晚於確認時間，才不再扣一次。不同帳戶、不同日期或金額不能沿用；不會把款項加回銀行餘額，也不會改寫任何股票成交。此私人確認不會隨 Git 發布，其他使用者更新程式不會套用別人的扣帳確認。

## 跨日歷史帳務核對

隔日查不到舊委託時，程式會查詢[可指定日期的已實現損益與買入來源](https://sinotrade.github.io/zh/tutor/accounting/profit_loss/)，並核對[目前持倉的買入明細](https://sinotrade.github.io/zh/tutor/accounting/position/)。這些查詢都是唯讀；不以「當日委託清單沒有舊單」作為未成交證明。

核對要求帳戶一致、日期範圍完整、查詢前後持股穩定，並用帳本已確認成交驗證歷史資料已更新。新委託會保存券商委託書號，與帳務 `dseq` 依日期、代號、買賣方向比對。部分已買入後又賣出的股數，會把已實現買入來源與剩餘持倉合計；只補記尚未記帳的累計成交差額。舊版沒有委託書號的委託，僅在該日該股完全沒有持倉或已實現買入來源等可核實的零成交情況自動解除，不能把同日其他手動單猜成策略單。

持倉明細的零股數量在目前 SDK 可能被截成整張數，0 張不代表 0 股。程式保留股數上下界，再用券商按股回傳的持股總數約束；只有能唯一確定的股數才補記。資料不全、存在多種零股分配、缺少可驗證的歷史成交、跨帳戶或身分衝突時，保留待確認並記錄具體原因，下次排程重新查詢。支援最多 31 個曆日的現股／現股淨額交割歷史；其他交易類型重疊時不猜測。

已過期的 ROD 委託以 `Expired` 記錄，與券商直接回報的撤單區分。原始回報、歷史資料摘要及證據識別碼留在本機帳本；不捏造成交。全部舊單釐清後，既有續跑流程依實際策略持股、原週期資金上限與當日行情計算剩餘目標。核對不會重複套用已記帳成交，已完成週期也不會重跑。歷史資料與帳本不隨 Git 發布。
